## 1. What version 1 does

`coursework` keeps a University of Melbourne student's coursework in one local place and lets an external
agent act on it safely. The owner works almost entirely in the local web UI; only configuration (login, MFA,
per-course AI policy) happens elsewhere.

| Area | User-visible result |
| --- | --- |
| Sync | Assignments, quizzes, weights, due dates, grades and course materials from Canvas and Ed land in a local database; changes since the last run become events ("due date moved", "new assessment", "grade released"). |
| Plan | A month/week calendar with teaching weeks, modules (school plus manual ones), manual and recurring tasks, a deterministic weekly plan that flags work that does not fit, and grade projection. |
| Assist | An external agent breaks assessments into steps; every step cites verified source text. |
| Revise | Revision notes and practice questions per course, generated by the agent with citations; a study page; objective questions graded locally, open questions graded by the agent; misses feed a weak-topic list. |
| Do | Graded autonomy per course and per assessment, L0–L4, gated by the owner's recorded course AI policy (section 4). |
| Talk | A chat panel in the UI that relays to a local external agent (Hermes); our code never calls a model. |
| Loop | Hermes runs scheduled sync, reacts to changes, regenerates plans and revision material, and pushes notifications. |

Out of version 1: iCal (#77), Notion (moved to version 2), multi-user hosting, minimal-change rescheduling, self-healing scrapers.

## 2. Architecture

```
Canvas / Ed
   │  capture: Playwright on the managed profile (replaced in C-2/C-3 by Codex reading in the owner's Edge)
   ▼
raw snapshots (.local/, never in git)
   │  normalize → redact → diff
   ▼
SQLite current-state tables  +  change_event (append-only, cursor)  +  run ledger  +  audit log
   │
   ▼
command registry (zod input/output per command)
   ├── CLI      (commander, `--json` envelope)
   ├── MCP      (@modelcontextprotocol/sdk, stdio)
   └── HTTP     (node:http on 127.0.0.1, /api/<command>) ── web UI (Vite + React)
                                                            └─ chat panel ── relay ── Hermes
```

- One command registry produces all three transports; business logic is written once (decision #30).
- Every agent write goes through a validating command; nothing writes the database directly except `src/store/`.
- Our code never calls a model (#13). Reasoning lives in the external agent; the UI chat is a relay.

## 4. Autonomy levels

| Level | Agent may | Who submits |
| --- | --- | --- |
| L0 | Read | — |
| L1 | Explain, find material, generate practice questions | Owner |
| L2 | Draft for the owner to edit | Owner |
| L3 | Produce the full answer and fill it in; owner reviews | Owner clicks submit |
| L4 | Produce, fill and submit | Code submits, after owner confirmation by default |

Rules (decisions #56, #57, #75):

- **Exams are never automated** at any level above L1.
- **Per-course AI policy record** is required before L2–L4: allowed / prohibited / owner-attested, with the
  source quote and location when one exists, or the owner's attestation and date when none exists. A course
  marked prohibited is capped at L1.
- **Per-assessment grant** sets the level, never higher than the course cap. Every grant, fill and submit is
  written to an append-only audit log.
- **L4 confirmation**: by default the UI shows the filled answers and the owner clicks "submit"; a per-course
  "auto-submit" switch removes that click.
- **Repository must be private before any L3/L4 answering or submitting code is pushed** (#57). Until the
  owner confirms the visibility change, that code stays on a local branch and is not pushed.
- Passwords stay out of model reach (existing red line); MFA stays with the owner.

## 6. Q1: the first Ed quiz

Decision #75. Goal: use the system on a real graded Ed quiz before 2026-10-25, without risking the grade on untested code.

1. Read the quiz questions from Ed's lesson JSON through the existing Ed transport (no `view=1`).
2. Expose them to the agent as a read command, after the redaction pass below; the agent proposes answers.
   Each proposal cites the question it answers, and any statement drawn from course material cites that
   material; the citation check (#63) runs on every proposal and rejects it on failure.
3. The owner reviews the answers in the terminal (UI comes in M3).
4. Playwright fills the answers into the open quiz page on the managed profile. **The owner clicks submit.**
5. During that submission, record the request Ed sends (method, path, body shape; tokens stripped) to `.local/`,
   so M4 can implement L4 through the endpoint instead of the page.

Q1 carries the minimum of M1 and M2 it needs, so no red line is skipped: a deterministic redaction pass over quiz
text before it reaches the agent (emails, student numbers, phone numbers, names from author fields); the citation
check; a per-assessment L3 grant read from a local file under `.local/`; and an append-only local audit log of
read, propose, fill and recorded-submission events. M1 and M2 later replace these with the full versions.

Before step 1 runs on real data: the course's AI policy is recorded as owner-attested (no course document,
2026-10-12), and the repository is private (section 4). Step 1's structure check is done by Claude on the
owner's profile, reading structure only, never copying quiz content into the repository.

Rejected: computer use (screenshot-driven clicking): slow, costly, non-deterministic, not a product feature.

## 7. Milestone designs

### M1 sync

- **Canvas**: same-origin GET of `/api/v1/...` (assignments, assignment_groups for weights, submissions for grades,
  modules and files for materials) inside the logged-in page, using the browser session, never a self-issued
  token (#58). First task is a spike that proves these reads work for a student account; if they are blocked, stop
  and ask before falling back to HTML parsing.
- **Ed**: JSON endpoints per #52; quiz and lesson structure from Q1.
- **iCal**: dropped (#77); Canvas JSON already carries due dates. M1 removes `ical` from `SourceItem.platform`
  (`src/domain/schemas.ts`) and from the domain-model spec.
- **Materials**: download linked PDFs to `.local/`, extract per-page text with unpdf, keep page numbers for citations.
- **Change detection** (#59): normalize each source into entities, compare field by field with current state,
  append `created` / `updated` / `deleted` events with a monotonically increasing cursor; consumers read
  `changes --since <cursor>`. Current-state tables remain the source of truth.
- **Redaction** (#60): deterministic. Names harvested from author and people fields in the data, plus regexes for
  emails, student numbers and phone numbers, plus owner rules and an allow-list (staff names). On by default (#19).
- **Run ledger**: start, end, pages/requests, failures, per-source coverage; this is where resume metrics come from.

### M2 protocol

- A registry entry is `{ name, input: zod, output: zod, handler, level }`. CLI subcommands, MCP tools and
  `/api/<name>` routes are generated from it; MCP input schemas derive from zod.
- **Citation check** (#63): both sides NFKC-normalized with whitespace and quotes unified; the quote must be a
  substring of the cited source; the stored citation records source id and offset (page number for PDFs). A
  failure rejects the write and is logged in the ledger. Applies to breakdown steps, revision notes and practice
  question explanations.
- Quiz answers and drafts are stored as proposals tied to an assessment; filling and submitting are separate
  commands gated by the level in section 4.

### M3 UI

- Vite + React single-page app reusing the prototype's CSS variables; built into `dist/ui` and served by the
  same process; `coursework ui` opens the browser.
- **Plan** (#65): deterministic earliest-deadline-first fill of
  each day's available hours; work that does not fit is flagged at risk, never dropped. Pure function, unit-tested.
- **Study page**: notes per course and week; practice questions; objective items graded in the browser, open
  items sent to the agent through the chat relay (#73); misses update a weak-topic list used by the revision plan.
- **Chat panel** (#72): relays to Hermes. A spike at the start of M3 confirms Hermes exposes an interface the local
  server can call; if not, stop and ask.

### M4 loop

- Hermes mounts `coursework mcp` (#66); a skill file describes the loop: sync → changes → breakdown/revision → plan → push.
- Revision is generated automatically when an exam is within a configurable window.
- L4 submit uses the Ed endpoint recorded in Q1 and keeps the confirmation default.

## 8. How development runs

Development runs unattended through a scheduled dispatcher session (#155, overriding #91); questions for
the owner are queued, not awaited. Claude dispatches, reviews and merges as below, and asks the owner at the points listed.

Per milestone: OpenSpec change (Codex drafts, Claude reviews) → issues → Codex implements (TDD for logic, #156) in a separate
clone → fresh-context Codex review → Claude commits, pushes, opens the PR → CI green for code PRs → Claude merges (#48) →
archive the change → acceptance checklist to the owner. Implementation and verification evidence goes in the
PR description, not in repository files (#90).

The owner is asked only for:

1. A design choice this file does not cover.
2. Steps only the owner can do: login, MFA, recording a course AI policy, changing repository visibility,
   acceptance runs, confirming an L4 submission.
3. A dependency outside section 3.
4. Starting a new session after a handoff (Claude Pro quota; #37, #39).

Acceptance checklist format: 3–5 numbered steps with the exact command or UI action and the expected result,
run on real data; the owner answers "pass" or names what is wrong.

## 9. Risks

| Risk | Mitigation |
| --- | --- |
| Canvas `/api/v1` blocked for session-cookie reads | Spike first; ask before switching to HTML parsing |
| Ed endpoints are undocumented and may change | Store raw JSON; tests on synthetic fixtures; failures are reported per source |
| Hermes has no callable interface for the chat relay | Spike at M3 start; ask before choosing another relay |
| Automated answering violates a course's rules | Course policy record, prohibited courses capped at L1, exams never, audit log |
| Repository private: GitHub Free has no branch protection for private repos | Local `guard.sh` still blocks pushes to `main`; CI still runs (2,000 free minutes/month) |
| Codex or Claude quota runs out mid-milestone | Handoff file, small issues, resume in a new session |
