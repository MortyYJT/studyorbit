# 同步管线优化记录

记录同步从「agent 逐页读网页」改为「代码采集 + 每门课一次模型调用」的过程和实测数字，供简历和面试使用。除「续跑和重来」一节外，所有数字都来自实际运行记录，来源写在每一节末尾；没有记录的值写「未记录」，不估算。「续跑和重来」一节用的是假模型和合成数据，里面的估算单独标出。

## 结论

四门课（COMP20003、COMP20008、MAST10007、MUSI20163）完整同步：

| 阶段 | 日期 | 做法 | 端到端耗时 | 模型输入 token | 模型输出 token |
| --- | --- | --- | ---: | ---: | ---: |
| 0. 原项目 | 2026-10-27 | 33 个 Codex 任务，每个任务自己开 Edge 窗口、用 computer use 复制页面 | 21 分钟 | 未记录 | 未记录 |
| 1. v2 初版 | 2026-10-28 | 每门课一个 Codex 调度任务 + 一个 gpt-6-luna subagent 读页面，串行 | 17 分 19 秒 | 8,817,416（缓存 8,262,272） | 61,429 |
| 2. 代码采集 | 2026-10-28 | 代码通过 Edge 后台标签读 Canvas 接口、用 edstem CLI 读 Ed；每门课一个 Luna 子任务整理，并行 | 206.4 秒 | 917,810（缓存 693,120） | 42,780 |
| 3. 单次调用 | 2026-10-29 | 采集同阶段 2，加 Handbook；每门课一次 DeepSeek Flash 结构化调用，并行 | **116.5 秒** | **44,269**（缓存 20,224） | 36,740（推理 23,130） |

从阶段 0 到阶段 3：

- 耗时：21 分钟 → 116.5 秒，约快 **10.8 倍**。和阶段 1 比，约快 8.9 倍。
- 模型输入：8,817,416 → 44,269，约少 **199 倍**（和阶段 1 比，阶段 0 没有记录）。
- 模型输出几乎没少（61,429 → 36,740）。DeepSeek 的推理 token 占了输出的大部分。
- Canvas 采集本身每门课 2–6 秒，不花 token。

## 为什么快了

1. **读数据的活交给代码。** 课程、评分组、作业、截止时间、分值和得分，Canvas 接口都直接给了。阶段 0、1 让模型逐页看网页再抄出来，每一步都要把整个上下文重新发一遍（阶段 1 的输入里有 94% 是缓存输入）。
2. **去掉 agent 中间步骤。** 阶段 2 还是 agent：要读文件、开子任务。阶段 3 改成一次 API 调用，输入就是采集好的数据，输出直接按 schema 返回。输入少了约 20 倍，主要就省在这里，不是换模型省的。
3. **采集串行，分析并行。** 浏览器同一时间只做一件事，免得抢焦点；模型分析可以并行，所以总耗时约等于最慢那门课（COMP20003）的耗时。

## 计算方法

- 阶段 3 的耗时：用量日志里每门课的 `at` 是开始时间，`durationMs` 是这门课从采集到保存的耗时。端到端耗时 = 最晚的「开始 + 耗时」减去最早的开始时间。COMP20003 最先开始也最后结束，所以结果就是它自己的 116.5 秒。不含点「同步」和选课的时间。
- token：取模型提供方报告的数字。输入包含缓存，输出包含推理，都没有重复相加。不同提供方的计数和价格不同，**token 少不等于费用按同样比例减少**。
- 来源：
  - 阶段 0：[第 0 阶段原始记录](sync-phase0-record.md)（proposal 原文 + 本机数据库里两次同步的时间线，21 分 05 秒和 20 分 29 秒）。
  - 阶段 1、2：[同步用量](sync-measurements.md)、混合同步实验（含个人成绩，本机私人记录，未入库）。

## 续跑和重来（假模型、合成数据，不是真实运行）

分阶段同步（`local-server-sync-pipeline`）把每门课拆成采集 → 分析 → 校验 → 合并四步，每步完成后在 `.local/studyorbit.db` 记检查点。同步中途停了，可以「继续上次同步」（续跑），也可以重新同步全部课程（重来）。这一节比较两者多花多少。

**本节所有数字都来自假模型、合成数据，不是真实运行。** 没有跑真实采集，也没有调用真实模型。

### 怎么测的

- 测试 `test/sync-faults.test.ts`，命令 `NODE_DEBUG= npx vitest run test/sync-faults.test.ts --silent=false`，测试结束时打印本节的数字。
- 四门合成课程（课程 ID 900001–900004），假采集器（每门课 Canvas、Ed、Handbook 各一次，直接写合成文件）和假模型（直接返回合成结果）。第 3 门课第一次分析故意返回不合格结果，要再调一次修复，所以一次完整同步是 12 次采集、5 次模型调用。
- 在每个阶段边界，第 2 门课做完这一步、记下检查点之后，模拟进程崩溃（`SimulatedCrash`）。此时第 1 门课已经全部完成，第 3、4 门课还没开始。合并边界的崩溃点在课程文件写完之后、检查点提交之前。
- 每个边界跑三种：
  - **不中断：** 一次跑完。
  - **失败 + 续跑：** 崩溃后重新打开数据库，用新任务续跑。
  - **失败 + 重来：** 同样崩溃后，新开一次全部课程的同步。
- 续跑的结果（桌面文件字节、快照哈希、课程状态和原因、变更记录）和不中断完全相同，这一点由测试断言，不只是看数字。
- 2026-10-30 在「运行环境」一节那台机器上连跑 5 次（Node.js 24.19.0）。token 和调用次数 5 次完全一样；耗时写 5 次的范围。

### 单位

- **假模型 token：** 每次调用按「提示词字符数 ÷ 4」加「回复字符数 ÷ 4」（各自向上取整）计，缓存和推理恒为 0。不是任何服务商的 token，不能换算成费用。合成课程的数据量差不多，第 1、2 门课的一次分析各是 2,949 个单位；真实课程之间差很多（见上面阶段 3 的表，输入 30,376 对 4,245）。
- **调用次数：** 写成「采集 / 模型」。一次采集是一门课的一个来源。
- **耗时：** 本机实际经过的毫秒数。假采集器和假模型没有任何等待，所以这里只量到管线本身的开销（哈希、SQLite 读写、文件检查），不代表真实同步的耗时。

怎么读：

- 每个边界「失败 + 续跑」都正好等于不中断：已经做完的采集和分析一次都没重做。
- 「重来多花」正好等于失败任务已花的部分：在采集 → 分析边界只有第 1 门课分析过（2,949）；之后的边界第 1、2 门课都分析过（5,898）。校验和合并不调模型，所以后三个边界的 token 一样。

- 第一行「不中断」的 22–23 ms 是这个测试文件里最先跑的一次，含预热，其他行约 10 ms。毫秒级的差别主要是固定开销和波动，不说明续跑在时间上更快或更慢。

### 换算到真实同步（估算，不是测量）

下面把上面的「哪些步骤不用重做」套到阶段 3 那次真实运行的每门课数字上（2026-10-28 UTC，即上表阶段 3 那次，墨尔本时间是 10-29；四门课按开始顺序是 COMP20003、COMP20008、MAST10007、MUSI20163）。**这是估算**：假设重做的步骤和那次花的 token、时间一样，实际每次运行都会不同。

先照搬测试场景，假设崩溃时第 1 门课已经全部完成：

| 中断位置 | 重来比续跑多花的模型 token（估算） | 重来比续跑多花的采集时间（估算） |
| --- | --- | --- |
| 第 2 门课采集完、还没分析（采集 → 分析） | 第 1 门课的分析：输入 30,376、输出 19,309 | 第 1、2 门课的采集：29.5 秒 + 10.9 秒 ≈ 40.4 秒 |
| 第 2 门课分析完之后（后三个边界） | 第 1、2 门课的分析：输入 35,579、输出 24,060 | 同上，约 40.4 秒 |

但那次真实运行的时间线和测试场景不一样：第 1 门课（COMP20003）分析了 87.0 秒，是最后结束的（约 15:17:50 UTC）。第 2 门课采集完（约 15:16:34）和分析完（约 15:16:56）时，第 1 门课都还在分析中；这时崩溃，进行中的分析没有检查点，续跑也要重做。按这条时间线：

| 中断位置 | 重来比续跑多花的模型 token（估算） | 重来比续跑多花的采集时间（估算） |
| --- | --- | --- |
| 第 2 门课采集完、还没分析 | 0（第 1 门课的分析两种做法都要重做） | 第 1、2 门课的采集，约 40.4 秒 |
| 第 2 门课分析完之后 | 第 2 门课的分析：输入 5,203、输出 4,751 | 同上，约 40.4 秒 |

- 采集不花 token，但慢：那次四门课串行采集合计约 51.0 秒（各课 Canvas + Ed + Handbook 相加），其中 COMP20003 一门就 29.5 秒（Ed 19.6 秒）。
- token 全在分析：四门课分析各 21.4–87.0 秒，花了全部 44,269 输入、36,740 输出 token。分析是并行的，所以省下的分析时间不能直接加到端到端耗时上，要看和别的课重叠多少；这里不给端到端的估算。
- 所以续跑省多少要看停在哪：停在前几门课的采集阶段，主要省时间；停在分析之后，主要省 token。

### 局限

- 没有测过真实同步。真实续跑还要经过已登录的浏览器和真实课程数据，不能无人值守地跑；用 DeepSeek 做真实测量没有得到授权（决定 #245 只授权了评测），见决定 #350。
- 崩溃点是挑好的：崩溃时没有别的采集或模型调用在进行。真实中断时，正在进行的那次调用会在续跑时重做，多花的部分比上表大。
- 合成课程之间假 token 差不多，而真实课程之间差 7 倍以上（输入 4,245 到 30,376），所以比例不能直接照搬到真实运行。
- 只有一种课程组合（4 门课、在第 2 门课处崩溃）。一般来说崩溃越晚，已完成的工作越多，续跑相对重来省得越多；这一点没有单独测。
- 耗时不含重新打开数据库和启动新进程的时间，也没有模拟网络和模型的等待（原计划的「模拟延迟」那一组没有跑，见决定 #435）。

## 局限（面试时要能说清楚）

- 每个阶段只完整跑了 1 次，只有 4 门课，只用了一个学生账号。不能说明在其他课程上一样稳定。
- 四个阶段读取的范围不同：阶段 1 读了教学资料目录，阶段 3 没读，但多读了 Handbook。比较的是「同一组课程跑完整同步」，不是同一份工作量。
- 快了不等于准了。阶段 3 仍有已知错误：COMP20003 的 A3 成绩接口返回 403；第一次分析把 A1 的 [已移除] 写成 [已移除]，改成按 lesson ID 关联后才修好；模型有时把分值当成权重。准确性靠人工核对四门课，没有自动化的准确率指标。
- 阶段 0 的两次运行里四门课的 Canvas 都没读到（记为 `absent`），见 [原始记录](sync-phase0-record.md#3-和后续阶段比较时要注意)。
- 阶段 0 是我自己早先的设计。这次的提升有一部分是在纠正那个设计，不全是外部瓶颈。
- 只在 macOS + Edge 上跑过。

## 简历写法（草稿）

英文：

- Re-architected a university coursework sync pipeline from LLM browser agents reading pages to deterministic API capture plus one schema-constrained LLM call per course; a full four-course sync went from 21 min to under 2 min, and model input tokens dropped from 8.8M to 44K (measured on real runs).
- Split responsibilities so that code extracts facts (IDs, due dates, points, grades) from the Canvas and Ed APIs and the model only interprets rule text (assessment weights in the handbook, hurdles, bonuses), with local schema and relation validation before saving.

中文：

- 把课业同步从「LLM agent 逐页读网页」重构为「代码读接口 + 每门课一次带 schema 约束的模型调用」，四门课完整同步从 21 分钟降到 2 分钟以内，模型输入 token 从 880 万降到 4.4 万（真实运行实测）。

面试可能会问：

- 当初为什么是 21 分钟？学校不允许学生自己签发 Canvas token，所以最早选了让 agent 读页面。后来发现在已登录的浏览器里可以同源调用接口，就不需要 agent 逐页读了。
- 怎么知道结果是对的？目前是逐门人工核对，并记录了已知错误。下一步是让代码生成稳定 ID，再对同一份采集数据分析两次，检查 ID、权重、分值是否完全一致。
- token 少了 199 倍，钱也少了 199 倍吗？不是。提供方和单价不同，缓存输入的价格也不同。
